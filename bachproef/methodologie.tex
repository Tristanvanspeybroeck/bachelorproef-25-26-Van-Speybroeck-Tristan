This research follows a design-oriented and experimental research design in which a proof-of-concept is developed and tested. The goal is to investigate to what extent AI techniques can be used for automatic error detection and feedback generation for the kip on bars. The emphasis is not on a fully validated coaching system, but on technically developing and exploratively assessing an analysis pipeline.

The research process is divided into five major phases.

\section{Phase 1: Literature study}

In the first phase, a literature study is carried out around three core components: 

\begin{itemize}
    \item biomechanical characteristics of the kip on bars and common errors
    \item markerless pose estimation in sports analysis
    \item automatic error detection and AI-based feedback systems
\end{itemize}

\textbf{Objective:} building a theoretical framework and estimating technical feasibility.  

\textbf{Deliverable:} developed literature chapter with justification of the chosen approach.  

\textbf{Research method:} systematic analysis of scientific publications and existing applications within sports analysis.

\section{Phase 2: Specification of error types and system requirements}

\subsection{Specification of detectable error types}

Based on the literature and practical experience within recreational gymnastics, concrete error types are defined that should be automatically detectable, such as bent arms or insufficient hip closure.

In addition, system requirements are drawn up that determine which functionalities the proof-of-concept must contain at minimum. This explicitly takes into account the practical context of recreational gymnastics, in which standard video footage and limited technical infrastructure are used.

In addition to these error definitions based on joint angles, the literature also points to the importance of critical intermediate points, or via-points, in the movement \autocite{Yamasaki2010}.

Within this research, these via-points are initially not explicitly modelled in the first version of the system. Instead, a simplified representation based on phases and joint angles is chosen, in order to first validate the technical feasibility of automatic error detection.

The integration of via-points as an additional analysis method is foreseen as a possible extension in an iterative development phase.

\subsection{System requirements}
\subsubsection{Functional requirements}

The functional requirements describe which functionalities the system must implement within the scope of the proof-of-concept. These requirements are considered development goals for a limited test setup.

\begin{enumerate}
    \item The system must be able to load a video fragment of a kip on bars.
    \item The system must automatically extract joint positions from the video through markerless pose estimation.
    \item The system must calculate relevant joint angles and store them in a structured CSV file.
    \item The system must divide the movement into relevant phases, namely the swing phase, pull phase, hip closure phase and support phase.
    \item The system must detect predefined technical errors based on pose data:
    \begin{itemize}
        \item bent arms during the pull phase,
        \item insufficient hip closure,
        \item early hip opening,
        \item weak shoulder push in the support phase.
    \end{itemize}
    \item The system must structure the analysis output in JSON format.
    \item The system must be able to generate textual feedback through a Large Language Model based on the errors that were actually detected.
    \item The system must prevent the LLM from generating feedback about errors that were not detected by the rule-based system.
\end{enumerate}

\subsubsection{Non-functional points of attention}

In addition to the functional requirements, several non-functional points of attention are formulated. In a full production system, these criteria would have to be evaluated quantitatively. Within this bachelor thesis, however, they are mainly used to guide the quality of the proof-of-concept. They are therefore not all formally measured.

\subsection{Prioritisation of requirements (MoSCoW)}

To clearly define the scope of the proof-of-concept, the functional requirements and non-functional points of attention are prioritised together according to the MoSCoW method. The prioritisation relates to the implementation of the proof-of-concept and not to a fully validated final application. This does not only consider the functionalities that must be technically implemented, but also the quality aspects that guide the development and interpretation of the results.

\textbf{Must have}
\begin{itemize}
    \item Video input for a kip on bars.
    \item Markerless pose estimation based on standard video footage.
    \item Extraction and storage of relevant joint angles in CSV format.
    \item Rule-based phase division of the movement.
    \item Implementation of detection rules for the four predefined error types.
    \item Structuring of the analysis output in JSON format.
    \item Generation of textual feedback based on errors that were actually detected.
    \item Prevention of the LLM generating feedback about errors that were not detected by the rule-based system.
\end{itemize}

\textbf{Should have}
\begin{itemize}
    \item Visual inspection of the calculated angle curves through graphs.
    \item Limitation of the LLM input to the errors that were actually detected.
    \item Safe handling when no errors are detected.
    \item Exploratory check of whether the pipeline gives reproducible output for the tested video attempts.
    \item Qualitative assessment of whether the generated feedback is understandable for a recreational gymnast and coach.
\end{itemize}

\textbf{Could have}
\begin{itemize}
    \item Visualisation of the skeleton on the video.
    \item Comparison of multiple attempts within the same pipeline.
    \item Further refinement of threshold values based on a larger dataset.
    \item Formal benchmarking of execution time and performance.
    \item Extensive user study with coaches and gymnasts.
\end{itemize}

\textbf{Won't have}
\begin{itemize}
    \item Real-time analysis.
    \item Mobile application.
    \item Fully automatic training platform.
    \item Fully validated coaching system.
    \item Automatic detection of errors outside the predefined error types, such as bent knees, toe position, head position or general elegance.
\end{itemize}

\textbf{Objective:} defining what exactly the system must detect and generate.  

\textbf{Deliverable:} list of error types, system requirements and corresponding measurable parameters.  

\textbf{Research method:} conceptual analysis and translation of biomechanical errors into quantifiable movement characteristics.

\section{Phase 3: Initial technical implementation of pose estimation and parameter extraction}

After defining the system requirements, a technical analysis pipeline is set up in a first development step, in which video footage is automatically processed through markerless pose estimation.

The video footage is processed using a Python-based pipeline. For this, the MediaPipe Pose Landmarker model is used, which performs markerless pose estimation on RGB video frames. The model used detects body landmarks per frame that describe the position of joints.

The detected landmarks are extracted and stored frame by frame, creating a time series of body positions. Based on these data, additional movement characteristics are calculated, such as joint angles. This first numerical representation made it possible to investigate in a next phase how AI systems interpret this movement information and to what extent automatic feedback generation is feasible.

\textbf{Objective:} converting standard video footage into usable pose data and interpretable biomechanical parameters.  

\textbf{Deliverable:} working pose estimation pipeline with CSV output and calculated joint angles.  

\textbf{Research method:} experimental implementation and technical validation of the data extraction.

\section{Phase 4: Exploratory AI experiment and rule-based system development}

Based on the extracted video data, pose landmarks and derived joint angles, it is then investigated to what extent existing Large Language Models are useful for automatic gymnastics analysis and feedback generation.

For this purpose, an exploratory experiment is carried out in which the same kip exercise is presented to the model in three different representations:

\begin{enumerate}
    \item raw video footage
    \item pose estimation data in CSV format
    \item a graphical representation of derived joint angles
\end{enumerate}

For each of these input forms, a similar prompt is used in which the model is asked to analyse the movement, identify phases and formulate technical feedback.

The findings from this exploratory experiment form the basis for the further development of the proof-of-concept. Because free multimodal interpretation appears to be insufficiently controllable, a rule-based approach is chosen in which predefined threshold values determine whether an error is present.

Given the exploratory nature of this research and the limited availability of labelled training data, a rule-based approach is deliberately chosen instead of a fully data-driven machine learning model. This approach increases the interpretability of the system and allows biomechanical criteria to be explicitly defined.

Although this rule-based approach mainly focuses on threshold values of joint angles, it partly aligns with biomechanical insights from the literature.

More advanced models, as described by \textcite{Yamasaki2010}, suggest that movements such as the kip are determined more by critical transition moments, or via-points. Within this proof-of-concept, however, a simplified implementation is chosen, in which these dynamic aspects are implicitly approximated through time-dependent changes in joint angles.

Detected errors are then converted into structured textual feedback through a Large Language Model.

To structure the output of the system and make it consistent, a standardised data format is defined in JSON form. This format contains information about the identified movement phases, calculated joint angles, applied detection rules and detected technical errors.

This structured representation forms the interface between the rule-based error detection and the feedback generation through a Large Language Model. The LLM is not used to detect new errors, but only to verbalise the errors identified by the rule-based system.

\textbf{Objective:} gaining insight into the limitations of free AI analysis and developing a controlled feedback pipeline based on this.  

\textbf{Deliverable:} a proof-of-concept system that structures biomechanical parameters, detects technical errors and generates automatic feedback.  

\textbf{Research method:} exploratory experiment combined with iterative system development.

\section{Phase 5: Evaluation}

Finally, the proof-of-concept is exploratively evaluated using a limited set of video attempts. It is examined whether the rule-based analysis detects no error in a good execution and whether the relevant error types within the scope of the system are recognised in incorrect executions.

In addition, the generated feedback is qualitatively assessed. This involves checking whether the LLM only gives feedback on errors that were actually detected and does not invent additional errors or improvement points.

This evaluation does not aim to formally validate the system, but to examine whether the full pipeline technically works and which limitations become visible within the tested attempts.

\textbf{Objective:} exploratively assessing whether the developed pipeline technically works within the limited test set.  

\textbf{Deliverable:} overview of the error detection, feedback generation and main limitations.  

\textbf{Research method:} exploratory test on multiple video attempts, visual inspection of graphs and qualitative assessment of the generated feedback.
